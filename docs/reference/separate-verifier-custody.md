# Separate verifier: custody reference

This page records exactly what a [separate verifier](../tasks/separate-verifier.md) does with the agent's outputs, and what each trial records. Read the task page first; this one is for reviewers and for debugging a refused or unscored trial.

## The trial, step by step

1. The agent runs in its sandbox as usual. Separate mode checks before the agent starts that the image has `python3` (3.10+) or `tar`, which capture needs. It installs nothing into the agent's image. It also measures, before the agent starts, the paths capture will read: the workspace, `/logs/artifacts` and each declared artifact (entries, bytes, and whether the path is a symlink). That measurement is the clean control for the failures below.
2. After the agent stops, its workspace is frozen into `evidence/` together with the declared `artifacts = [...]`, and `/logs/artifacts` is collected into `artifacts/`. This is the same capture `--freeze-workspace` and `bench regrade` use. Images without Python are captured with `tar` alone. Then the steps that still read the agent's sandbox run (skill export, the usage proxy's stop, the egress proxy's stop, the session-log price), and the agent's sandbox is stopped and deleted (only stopped, when containers are kept). No process of the agent's run is left to change what crosses. A stop that fails (it raises, runs past 5 minutes, or leaves the sandbox up: after the stop BenchFlow lists the compose project's containers on Docker and remote Docker, and checks the sandbox's state on Daytona) is logged and recorded as `custody.agent_stop_error` in `verifier-sandbox.json`; the trial is still verified and scored as usual, and the sandbox is stopped again at cleanup.
3. The host packs exactly those files into one archive, after checking every byte against the manifest written at capture. Nothing else is read from the agent's sandbox. On Docker, `/logs/artifacts` is a live bind mount of the trial's `artifacts/` folder, so each of its files is opened once, without following a symlink anywhere on its path, checked to be a regular file, and copied into a private folder; that copy is what is hashed and packed. A file that changed since collection, or is no longer a regular file, leaves the trial unscored.
4. A fresh verifier sandbox starts from the verifier image. It needs only the task's files, so on Docker and remote Docker it starts when the agent's turn begins (its sandbox is ready and the agent installed), and is ready by the time step 3 has packed the archive; on Daytona it starts once the agent's sandbox has stopped. A trial that ends before verifying (the agent errored, the run was stopped) deletes it at cleanup. The archive is unpacked at the original absolute paths. A dedicated workspace such as `/app`, `/testbed` or `/workspace` replaces the contents of the image's copy, so a file the agent deleted or renamed stays gone; a shared directory such as `/root` or `/tmp` is laid over the image instead. Files and directories get the permission bits the solver left, as in a regrade, and belong to root. The normal verifier path then runs there: hardening, upload of `tests/`, `test.sh`, reward parsing. Hardening knows the sandbox is fresh: the pytest plugin guard distrusts only the paths the archive wrote and `/logs`, not the image's other directories or their modes (see [Pytest plugin guard](../sandboxes/threat-model.md#pytest-plugin-guard)). Its outputs become the trial's `verifier/` (see [What crosses](#what-crosses-in-detail)).
5. The verifier sandbox is deleted.

### Later starts

`BENCHFLOW_VERIFIER_PREPARE=entry` starts the verifier sandbox when the agent finishes, while step 2 runs (the order without the warm-up). `BENCHFLOW_VERIFIER_PREPARE=serial` keeps the older order: the verifier sandbox starts after step 3, and the agent's sandbox stays up until the trial's cleanup, after the verifier. The same order applies when the sandbox belongs to the caller (`use_prebuilt_env`) and when `verify()` is called outside `run()`'s own lifecycle (an SDK caller or a branch child that may still use the sandbox); `verifier-sandbox.json` then has `order: serial` and `agent_sandbox_alive_during_verify: true`.

## What crosses, in detail

Some paths in the verifier sandbox belong to the verifier: `/tests`, `/verifier`, `/logs/verifier`, `/logs/agent`, and hardening's own `/_benchflow_verifier_*` and `/_benchflow_guard_*`. A workspace or declared artifact that equals one of them, lies under one, or contains one (a workspace of `/logs`, say) never crosses:

- declared in task.toml (an artifact, or `[sandbox].workdir`), it is refused before launch under `verifier.sandbox.transfer`; `bench check` and `--integrity strict` print it;
- declared by a run overlay, by an SDK caller that skips the launch check, or taken from the image's `WORKDIR` (only the started sandbox knows it), the trial is unscored: `verifier_error` reads `separate verifier transfer failed: <path> overlaps verifier-owned <path>` and the status is `transfer_failed`. These paths come from the task and the run, not the agent, so a retry repeats the refusal;
- a declared artifact that capture resolved into such a folder through a symlink the agent left on its way (`/app/out` pointing at `/tests`) scores 0 as `refused` when the same path resolved elsewhere before the agent ran, and is unscored otherwise. What is judged is where each archived file lands, so a link swapped in after the artifact was found and before it was copied is caught the same way;
- a declared artifact copied from somewhere other than where it was found (a link swapped in between, pointing outside these folders) leaves the trial unscored, as any change during capture does.

### Every root must land where it was declared

Every packed root must also land where it was declared. The workspace must be captured at the agent's working directory, and each declared artifact at its declared path (a relative one joined to that directory), or where that path resolved before the agent ran (a link in the task's own image, `/out` pointing at `/data`, say). A root that a link on its way moved anywhere else (the agent made `/out` a link to `/usr` before the declared `/out/bin` was found, so `/usr/bin` would cross over the verifier image's tools) scores 0 as `refused` when the clean control saw where the path resolved, and is unscored when it could not. A folder that lands in, or holds files for, a system folder (`/bin`, `/sbin`, `/lib*`, `/etc`, `/boot`, `/dev`, `/proc`, `/run`, `/sys`, `/usr/bin`, `/usr/sbin`, `/usr/lib*`, `/usr/libexec`, `/usr/local/bin`, `/usr/local/sbin`, `/usr/local/lib`) leaves the trial unscored even when declared that way: it would replace the programs `test.sh` runs. The exception is a folder the solution made where the clean image had none (the task declares the file `/usr/local/bin/tool`, and the agent left a folder there): that scores 0 as `refused`. The one file a task declares there (`/usr/local/bin/tool`) still crosses, and only it; a file that resolves into one from anywhere else does not.

### Links in the verifier image

The same rules hold where the transfer lands in the verifier sandbox. Before anything there is emptied or unpacked, BenchFlow checks every folder on the way to each packed file for a link the verifier image itself keeps (tar follows such a link). A link that would put a file in `/tests`, `/verifier`, `/logs/verifier`, `/logs/agent` or a system folder (the verifier image has `/out` linked to `/usr`, and `/out/bin` is declared), or that leads to no folder, leaves the trial unscored: it is the task's images that disagree. Any other link is the image's layout: the transfer crosses, and the record's `custody.destinations` lists each link it went through and where it led.

### The trial's verifier folder

Back in the trial folder, `verifier/` holds exactly what the verifier sandbox wrote to `/logs/verifier`. The folder the agent's sandbox could write (on Docker it is the agent container's `/logs/verifier` mount, still live when the verifier finishes in the serial order) is moved to `verifier-sandbox/agent-verifier-dir/` and a staged copy of the verifier's outputs is renamed into its place. A process left running in the agent's container keeps writing into the moved folder, never into `verifier/`. Should the agent have made that folder impossible to move into `verifier-sandbox/` (moving a folder to another parent needs write permission on the folder itself), it is moved to `agent-verifier-dir/` in the trial folder instead. Either way `verifier-sandbox.json` lists it under `planted_in_verifier_dir`. Job export, reward provenance and the task.md `timed_out` record therefore read only the verifier's files, and a file planted under a verifier output's name (a root-owned `reward.txt`) can no longer block the copy and turn a scored 0 into an unscored trial. When the verifier never ran (an unscored trial), `verifier/` is left empty.

## Which failures score 0

A transfer into a verifier-owned folder is unscored the same way (see [What crosses](#what-crosses-in-detail)), as is a verifier image whose build context holds a compose file with services besides `main`: the `environment/Dockerfile` fallback copies the task's whole `environment/`, and its side services would start a second time beside the verifier. Such a task is refused before launch under `verifier.sandbox.services`; give it a `tests/Dockerfile` or a `[verifier.sandbox]` `docker_image`.

Some of these causes are the solution's own files: a workspace over the capture limits, `/logs/artifacts` over the collection limits (the agent owns that directory), a declared artifact left as a symlink, or a file in `/logs/artifacts` that takes a declared artifact's place. When the same paths were within bounds before the agent ran, the trial scores 0: `rewards` is `{"reward": 0.0}`, there is no `verifier_error` (so a retry cannot resample the 0 away), a verifier sandbox already started for the trial is deleted without receiving anything, and `verifier-sandbox.json` has `status` `refused` with the reason in `refusal`. A policy therefore cannot turn a low score into an unscored trial by making its outputs impossible to transfer. When the clean control shows the same problem (a task image whose workspace is already over the limits, say), or it could not be measured, the trial stays unscored as above.

A symlink that points out of the workspace is not a failure at all: capture leaves it out and lists it in the manifest's `exclusions` (`symlink_escape`, with its `link_target`), so a virtualenv's `bin/python` or an agent CLI's helper link costs nothing.

### Collected artifact links

Collected artifact links have a narrower contract. Mounted and copied collection keep a link only when its original target is a plain relative path within that collection, with no empty, `.` or `..` components and no other links along the path. Accepted target bytes remain unchanged. Absolute paths, trailing `/` or `/.`, and link chains are refused even when they would stay inside the collection. `artifacts-manifest.json` records each refusal as `symlink_refused` with the original target; a separate verifier receives no file at that link's path.

## Records

Except in the serial order, the agent's sandbox is stopped before the verifier sandbox receives anything. With the default start, on Docker and remote Docker the verifier sandbox exists beside the agent's for the agent's whole turn, so you pay for both during that turn. With `BENCHFLOW_VERIFIER_PREPARE=entry` it starts when the agent finishes; in the serial order (`serial`, a sandbox that belongs to the caller, or `verify()` called outside `run()`) it starts after the archive is packed, and the agent's sandbox stays up until cleanup (see [Later starts](#later-starts)). On Daytona, outside the serial order, the verifier sandbox starts once the agent's sandbox has stopped, so the two overlap only when that stop fails: the agent's sandbox is then billed, and counted as overlap, until cleanup stops it. Each trial records:

- in `timing.json`: `verifier_pack` (checking and packing the archive), `verifier_sandbox_setup` (create and build), `verifier_transfer` (upload and unpack), `verifier` (hardening and `test.sh`), `verifier_sandbox_teardown` and `verifier_sandbox_total` (the verifier sandbox's life; in the serial order from the start of packing); `agent_release` (the steps that read the agent's sandbox, and its stop) and `agent_sandbox_stop_before_verify` (the stop alone), `verifier_sandbox_ready_wait` (how long scoring waited for the verifier sandbox once the archive was packed) `verifier_sandbox_warmup` (the verifier sandbox's seconds during the agent's turn, before scoring began; with the default start only) and `verifier_sandbox_overlap` (the seconds both sandboxes existed from the moment scoring began, or from the verifier sandbox's start when it started later); and, in every mode, `agent_stop_to_reward`, from the agent's end to the rewards;
- in `verifier-sandbox/verifier-sandbox.json`: `image_source`, `sandbox_id`, `order` (`overlap`, or `serial` for the older order), `agent_sandbox_alive_during_verify`, `status` (`complete`, `verifier_failed`, `transfer_failed`, `sandbox_failed`, `refused`; `abandoned` or `interrupted` when the trial failed or was cancelled before its transfer, and the started verifier sandbox was deleted), the transfer inventory (workspace, files, bytes, declared artifacts, missing artifacts, `/logs/artifacts` files, exclusions), `pristine` (the measurement before the agent, with where each path resolved), `sandbox_seconds` (the verifier sandbox's life, from its start to its deletion), and the error or, for `refused`, the `refusal`;
- in the same file, `verifier_layer`: whether the verifier image was reused (`hit` or `miss`, the key, seconds and lock wait), with `cache: image-only`; `BENCHFLOW_VERIFIER_LAYER=1` opts into eligible image reuse across the task's trials without installing or seeding tools ([verifier image reuse](../jobs/cache.md#verifier-image-reuse));
- in the same file, `custody`: the archive's `tar_sha256` and `tar_bytes`; `members`, one entry per root (the workspace, each declared artifact's folder, `/logs/artifacts`) with the paths unpacked under it (the first 1,000), their `count` and a `members_sha256` over all of them; `destinations`, each verifier-image link the transfer went through (`path`, `resolves_to`), usually empty; `sha256_checked_in_sandbox` (`true`, or `false` when the verifier image has no `sha256sum`); `agent_stop_error` (null, or why the agent sandbox did not stop before the transfer); and `trajectory` (`source`, `path`, `bytes`, `sha256`) for the trajectory published to `/logs/agent`;
- also there: `planted_in_verifier_dir` (where the agent-writable folder went, `moved_to`, and each entry's `name` and `type`, with `bytes` and `sha256` for a file the host can read or `unreadable: true`; the first 1,000 entries and the `total`; only those entries are read, at most 256 MiB in all, so a file over 64 MiB or past that budget (the listing then says `hash_budget_exhausted: true`) has `bytes` but no `sha256`) and `published_verifier_files` (the same listing of the published `verifier/`);
- `verifier-sandbox/sandbox.json`: the provider id, written as soon as the sandbox exists.

A job's `--max-sandbox-seconds` budget adds `verifier_sandbox_overlap` to each trial's wall-clock time: the wall clock already counts one sandbox at a time. The `verifier_sandbox_warmup` seconds are not charged, so a verifier sandbox started during the agent's turn is charged as one started when scoring began. A trial in the serial order adds its whole `verifier_sandbox_total`.
